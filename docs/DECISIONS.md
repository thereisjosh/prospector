# Decision log — Prospector agent (v2-engine)

§ = `docs/SPEC-agent.md`. **Smoke** = `eval/recordings/agent-icp1-2026-10-12/agent/` (12 turns, $0.87, 6 leads). **Pilot** = `eval/results/pilot-2026-10-12/` (judged; final scores in `report.md`).

| # | Decision | Alternatives | Why (evidence) | What would change it |
|---|---|---|---|---|
| 1 | Stateless Messages API, hand-written loop, one turn per request | LangGraph; OpenAI Agents SDK; Claude Managed Agents | Every step visible (§3). Durable pause = persist append-only history: LangGraph's checkpointer + `interrupt()` in ~30 lines (§5a); short requests fit serverless (§13). Tests: `save/load round-trips messages byte-identically`, `resumes from a saved state after a crash mid-run` | Needing sandboxed execution or multi-hour background work |
| 2 | Opus 5.5 default; Sonnet 5.5 as arm C | Sonnet default; one model | Model is config (`src/agent/config.ts`); cost per lead is a headline metric (§3, RUBRIC §4). Claude was $0.42 of smoke's $0.87 | Arm C matching B on pass^3 at lower cost per good lead |
| 3 | 8 narrow tools; no "run any query" tool | Raw Exa passthrough; generic fetch | Tools apply the plan's schema and `excludeDomains` in code (§4). `submit_lead` is the only write path, so injected text can at most cause a submit that still faces every gate (§5). Test: `state.leads only contains checker-accepted leads even if final text claims more` | Traces showing a missing capability → add a narrow tool, not a generic one |
| 4 | Plan = contract, not script | Fixed query list (workflow, arm A) | §2. The 2026-10-11 workflow rejected 47 candidates, mostly size, without changing a query (`docs/prompts.md`). Smoke: 12 self-written queries, 2 rewrites, 41 lookups skipped | Most runs flagged "workflow-shaped" (RUBRIC §6), or A ties B on pass^3 for less |
| 5 | Approve contract, strategy, scope changes; not each action. No framework interrupt | Per-action approval; full autonomy; `interrupt()` | Smoke made 43 tool calls, none with external side effects (§5a). Strategy-before-spend enforced in code (test `A2b #6`); decisions bound to the pending tool_use id (`F1.5`) | High decline rate (friction not earning its keep) or near-100% approval (auto-approve under a cost) |
| 6 | Model proposes, code decides (`checkLead`) | LLM self-judging; prompt-only rules | One lead definition for both arms (066eee5). Code bounds real Exa failures: year-slip dates, 356 vs 3,560 headcount (§5). `eval/gates.test.ts`: one test per gate code | Judge finding accepted leads failing Q1 at a rate gates cannot reach |
| 7 | Handback, never self-widening | Agent relaxes criteria itself | The plan is the user's (§5). Smoke's handback suggested an un-actionable `scope` → structured, data-driven handback (8f33f2b; test `never emits field 'scope'`) | Sim-user re-runs with suggestion #1 adding no good leads (RUBRIC `handback_quality`) |
| 8 | Memory: seen-list in code; 👎 reasons in first user message | None; notes in system prompt | Otherwise re-runs repeat leads (§6a); system prompt stays cacheable (§6). Test: `memory feeds seen names, appends run outcomes, and preference notes enter the first message` | Same 👎 reasons recurring despite the notes |
| 9 | No subagents; no agent-to-agent handoff | Lookup subagents; outreach handoff | Handoff adds external side effects and does not address lead quality (§5). Smoke's last turn read 42.5k cached tokens; the 30-turn cap bounds context (§6) | Larger targets (e.g. 50 leads) degrading quality as context grows |
| 10 | Exa is the only retrieval layer | Multiple search APIs; scraping | Every output fact comes from Exa (SPEC-v2 §1), behind one cost guard and record/replay (`src/exa.ts`) | Exa extraction errors that gates cannot bound (§13) |
| 11 | Hard combined Exa + Claude $ cap, enforced by the harness | Prompt-stated budget; Exa-only cap | §5 limits; Claude spend reserved per call (`F1.2`); CostGuard breach stops the run (`F1.3`); $0.05 handback reserve. Pilot agent runs all ≤ $0.86 of $1.00; S2 workflow aborted 3/3 on the cap pre-check → graceful degradation (f2bd783) | `budget` stops dominating runs that were still finding good leads |
| 12 | pass^3 headline, pass@1 alongside | Mean good leads; pass@1 only | "A user needs it to work every time" (RUBRIC §3); math tested (`H5`). Pilot: it separates the arms on both scenarios (agent 1, workflow 0, `report.md`) | pass^3 = 0 for every arm (no signal at n = 3, RUBRIC §7) |
| 13 | Free `count_tokens` preflight | Discover schema errors on a paid turn 1 | `eval/check-tool-schemas.ts`; the strict-schema fixes in 9ff1b21 (`minimum`/`maximum` unsupported) are the class it catches at $0 | An error that passes `count_tokens` but fails `create` |
| 14 | Judge = Opus 5.5 with `web_search` (max 3) + `web_fetch` (max 2), signal page fetched first; corroboration allowed when the page blocks fetches | Search-only judge (v2); Sonnet judge; human-only labels | The search-only judge could not open signal URLs: S1 8/22, S2 10/23 good. Re-judging its Q3 "cannot verify" verdicts with fetch: S1 14/22, S2 15/23 (FAILURES #10). Cost: v2 $8.64 for 45 verdicts (≈ $0.19 each, `*/judge-cost.json`); v3 $5.75 for 17 re-judges (≈ $0.34 each, `costDollars` in the `v3-fetch` verdicts). Human spot-checks 10/45 (22%) agree with the final verdicts; the one disagreement (RGL, v2) triggered v3 (`eval/truth/SPOT-CHECKS.md`) | Spot-checks disagreeing with v3 verdicts; a cheaper judge matching Opus on the spot-checked set |
| 15 | Target segment: mid-market B2B with a public footprint (logistics, SaaS, funded startups, manufacturers) | Local small businesses; enterprises; every B2B seller | Works: S1 logistics, agent 9 / 7 / 6 good leads, $0.12 per good lead; S2 funded B2B, 8 / 8 / 8, $0.09 (pass^3 = 1 on both, `eval/results/pilot-2026-10-12/report.md`). Counter-example: a user run on 2026-10-13 against Singapore pet businesses (size 2–100) returned 3 of 10 leads, and the agent's handback said it "couldn't find reliable company details for small local businesses" and that records matched a similarly named company overseas. That run is on the server, not in the repo. Enterprises are excluded by design (`enterprise` gate + exclusion lists) | A different evidence source (e.g. a local business registry) that lifts local-business runs to the S1/S2 level |
| 16 | 98% bar: evidence-required gates and candidate tier; recall is the variable | Trust Exa's yes/no summaries; reject every unknown; accept with a confidence penalty | Pilot precision missed the product bar (S1 0.88, S2 0.80) because summaries guessed required booleans and non-event pages counted as signals. New schemas require verbatim quotes, code checks quotes against captured page text, and missing required proof becomes a candidate rather than an accepted lead. Replay projection: `eval/results/gate-replay-2026-10-14.md`; tests: `eval/gates.test.ts`, `eval/agent.test.ts`. | Fresh quote-enabled pilot still losing too many good leads, or quotes proving unreliable despite substring verification |
| 17 | Memory: ranked recall behind one seam, per-type expiry, provenance; no vector store, keyword overlap is enough at this scale | Embedding/vector store; put all notes in every prompt; one flat note list | A fact has one home by who may act on it: constraints in code, preferences and episodic notes in the model's first message, working state in the run (§6a). One function, `recall()`, is the only reader, so which memories shaped a run is one `memory_recalled` event. At this scale (≤ 200 notes, a handful of preferences, ≤ 800 prompt tokens) tags and plan words already separate relevant from irrelevant; a vector store would add a dependency and an opaque score. Tests: `eval/memory.test.ts` (ranking, expiry, budget, migration, supersession, eviction, `remember` limits) | A workspace regularly holding hundreds of live notes whose tags do not overlap the plan, or `memory_recalled` traces showing the right note excluded |
| 18 | Working memory: full history persisted, re-sent under a token budget; dropped turns replaced by a code-written summary from state, never a model summary | Re-send everything (bounded only by turn cap and dollars); model-written summary | The model remembers nothing, so history is a table plus a function that decides what to re-send (`src/agent/context.ts`). A model summary can launder a wrong claim into "memory"; the code summary is built only from leads, rejections, spend and query caches (§2a). A crashed turn leaves a dangling `tool_use` that 400s the next call, so `loadState` repairs it (§5a) | Real runs that approach 60% of the window show the summary losing something the model needed; or a measured context window that differs from the 200,000 assumed |
